## §2 Task 2 — TODO 3.4: Plugin nav routing by manifest scopes [P1]

### §2.1 Problem

`AppShell.tsx` renders every enabled plugin nav link by URL-param presence (`clientId ? client-scoped : global`). That conflates *where the user is* with *how the plugin is configured*: a client-scoped plugin appears on the dashboard with a global link (where its config endpoint would be queried at the wrong scope), and a global plugin gets a client-scoped link while inside a client's feed pages. The spec (§3) says plugins declaring `'client'` in their scopes must route under `/clients/:clientId/plugins/:pluginId`.

### §2.2 Change

In `AppShell.tsx`, for each enabled menu-item plugin, read scopes from the manifest:

- Extraction is safe/parsed: `manifest?.config_scope` / `manifest?.data_scope` may be string | string[] | undefined (backend `_parse_scope` defaults missing to `('global',)`; frontend `PluginInfo.manifest` is `{ [key: string]: unknown } | null`). Normalize to string arrays; treat malformed values as absent.
- A plugin is **client-scoped** iff `'client'` ∈ config_scope OR `'client'` ∈ data_scope. (`'feed_source'` scope does not affect nav routing — it is not a nav concept.)
- Client-scoped plugin + `clientId` in URL → link `/clients/${clientId}/plugins/${pluginId}`.
- Client-scoped plugin + no `clientId` → **hidden from nav** (no disabled row — a disabled row implies "available later"; hidden matches the approved design and TODO acceptance).
- Otherwise (global) → link `/plugins/${pluginId}`.

No router changes: both routes exist (`router.tsx`), `PluginPage` already reads `clientId` from `useParams`.

### §2.3 Tests (AppShell.test.tsx)

- Global plugin (scopes global) → link `/plugins/x`.
- Client-scoped plugin (`config_scope: ['client']`) rendered while on a client page (`/clients/1/...`) → link `/clients/1/plugins/x`.
- Same plugin on a non-client page (dashboard) → not rendered in nav.
- Plugin with `data_scope: 'client'` (but global config) → treated client-scoped.
- Manifest without scope fields → defaults global.
- Manifest with malformed scope values (e.g. `config_scope: 42`) → treated global, no crash.

## §3 Task 3 — TODO 1.7: Route error boundary for chunk-load failures [P1]

### §3.1 Problem

Task 4.1 (2026-08-30) lazy-loads all 9 feature pages. After a deploy, a stale tab navigating to a not-yet-loaded chunk gets `Failed to fetch dynamically imported module` and react-router's `DefaultErrorComponent` — raw "Unexpected Application Error!" + stack trace, no retry. This is the most common post-deploy user-visible failure; a reload always fixes it.

### §3.2 Change

`frontend/src/app/router.tsx`:

- New `RouteErrorBoundary` component: when the caught error looks like a chunk-load failure (`error instanceof TypeError` with "fetch" / "import" in the message — established vite pattern) it renders a friendly message; for any other render/route error it renders the same friendly layout with a generic message. Both variants offer a single primary action: **Reload** — `window.location.assign(window.location.href)`.
- Mounted as `errorElement` on the `AppShell` child route object that carries the lazy pages (the route element `<AppShell/>` gets `errorElement: <RouteErrorBoundary />`), so all 9 lazy children are covered without adding an errorElement per route.
- The 401/session-guard behaviors (tasks 3.1/3.2) are untouched: `makeUnauthorizedHandler` clears the session cache and navigates to login before any boundary renders; `RequireSession`'s 401 branch still `Navigate`s to `/login`.
- No stack traces rendered. No new state; purely presentational. Uses existing `ErrorState` visual language but with the reload action (ErrorState takes `onRetry` — reuse if its label fits, otherwise a small local variant).

**i18n** (`common.json`, en+de identical): `errors.chunkLoadFailed`, `errors.routeError` (generic variant), `errors.reload` (button label).

### §3.3 Tests (router.test.tsx)

- A route whose lazy `import()` rejects (mock the dynamic import to reject with a TypeError "Failed to fetch dynamically imported module") renders the friendly boundary with the Reload button — not react-router's default error UI ("Unexpected Application Error" absent).
- Clicking Reload navigates: assert `window.location.assign` called with current href (mock `window.location`).
- Non-chunk render error (e.g. a route element that throws a normal Error) → same friendly boundary, generic message, Reload present.
- Existing tests (401 redirect, session reset, 503 ErrorState, retry) stay green.
